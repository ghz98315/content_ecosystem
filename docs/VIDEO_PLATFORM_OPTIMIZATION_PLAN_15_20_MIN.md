# 视频平台优化计划：可用成片展示与 15-20 分钟产出目标

## 目标

1. 失败的重跑不遮挡最近一次可用成片。
2. 900 秒超时保留为内部故障信号，不作为用户主要内容展示。
3. 单条正常任务从提交到成片目标控制在 15-20 分钟。
4. 每个阶段可观测、可重跑、不会混用旧产物。

## 一、成片错误展示策略

### 必须保留的内部状态

- render 超时必须写入 stage error，便于 Worker、日志和自动质检追踪。
- 失败阶段不得标记为 done。
- 失败任务不得被下游阶段继续认领。
- 旧 `final.mp4` 不得被失败重跑覆盖。

### 页面展示调整

- 如果存在最近一次成功的 `final.mp4`，播放器继续显示该成片。
- 将“本次 render 重跑失败”降级为提示，不用红色错误块覆盖播放器。
- 页面文案建议：`本次重跑未完成，当前显示上一次成功成片`。
- 只有在没有任何可用成片时，才显示明显失败状态和重跑按钮。
- 质检报告仍保留，但放在播放器下方或折叠区域。

### 验收标准

- render failed 时仍能播放和下载旧成片。
- render pending/processing 时仍能查看旧成片。
- 新成片只有在质检通过并上传成功后才替换当前产物引用。
- 页面不把“旧成片可用”和“本次重跑失败”混成一个状态。

## 二、15-20 分钟产出时间预算

以常规 40-45 个镜头为目标，建议预算如下：

| 阶段 | 目标耗时 | 优化方向 |
| --- | ---: | --- |
| ingest/transcribe/clean/rewrite | 1-3 分钟 | 保持现有并行和重试 |
| image 生图 | 5-9 分钟 | 九宫格批量生成、断点续跑、避免重复请求 |
| image 切割与下载 | 1-2 分钟 | 并行下载、校验后缓存 |
| book | 10-30 秒 | 保留人工确认门槛 |
| TTS | 1-3 分钟 | 长文本分段并行、音频拼接后统一测时 |
| render | 3-6 分钟 | 减少 ffmpeg 进程、长时间轴硬切降级、统一编码参数 |
| 质检与上传 | 30-90 秒 | 本地先检查，合格后一次上传 |

## 三、实施顺序

### P0：先稳定结果展示

- 完成“旧成片可用、错误降级”的页面策略。
- 验证失败、重跑中、成功三种状态。
- 不修改音色和视觉样式。

### P1：建立时间指标

- 记录每个 stage 的开始、结束、耗时。
- 记录图片数量、TTS 时长、镜头数量、render 子进程数量。
- 将总耗时拆分为等待、网络、CPU、ffmpeg 四类。

### P2：优化生图阶段

- 保持九宫格，不切换 16 宫格。
- 已成功的 grid 和单图不重复生成。
- 对超时请求使用有限重试和断点续跑。
- 并行度以 Provider 限流和本机 CPU 为约束，逐步压测。

### P3：优化 TTS 阶段

- 先保留 Edge TTS 作为 fallback。
- 独立试听 CosyVoice2/Index-TTS2，不直接覆盖生产音频。
- 确认音频真实时长后再生成字幕和画面时间轴。

### P4：优化 render 阶段

- 统计每个镜头编码耗时。
- 统一使用快速编码 preset，并限制并发资源。
- 24 张以内保留叠化；长时间轴默认保留 zoom in、采用硬切，避免多轮 xfade 叠加。
- 后续再研究单次 ffmpeg filter graph 的柔和过渡，不能影响 15-20 分钟目标。

### P5：页面统一优化

- 任务列表显示阶段耗时、预计剩余时间和最后更新时间。
- 阶段详情统一状态、产物、错误和重跑操作。
- 成片页优先展示播放器，再展示质检和诊断信息。
- 自定义域名和 Vercel 域名统一账号后，再进行视觉细节优化。

## 四、每阶段验收门槛

- P0：旧成片不会因失败重跑而消失。
- P1：可以准确得到整条任务和各阶段耗时。
- P2：图片阶段可从中断处继续，不重复支付已成功请求。
- P3：TTS 音频、字幕和图片时间轴对齐。
- P4：标准任务 render 不再触发 900 秒超时。
- P5：桌面端、移动端和自定义域名均能完成核心操作。

## 当前建议

先执行 P0 和 P1，再开始页面整体美化。没有耗时数据直接做页面优化，无法判断瓶颈是在生图、TTS 还是 render，后续容易重复修改。

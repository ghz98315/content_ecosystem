# 双人对话播客视频初步规划

> 文档状态：规划中，未开发  
> 主阶段：规划阶段  
> 当前优先级：低于现有单人图文解读流程优化  
> 制定日期：2026-08-07  
> 启动条件：现有八阶段主流程完成样片验收并形成稳定基线

## 1. 文档目的

本文档用于提前明确双人对话播客视频的产品边界、工作流、数据契约、实现顺序和验收标准。

双人播客是独立创作模式，不向当前单人图文解读流程追加阶段，也不在当前优化期修改现有八阶段顺序：

```text
当前单人流程
ingest → transcribe → clean → rewrite → image → book → tts → render

未来双人播客流程
podcast_prepare
  → podcast_script
  → podcast_review
  → podcast_tts
  → podcast_visual
  → podcast_render
```

两套流程可以复用任务、产物、Storage、Worker、字幕时间轴和 FFmpeg 等基础设施，但业务阶段、页面和产物版本必须隔离。

## 2. 为什么暂不开发

当前应优先完成单人图文解读流程的稳定性和成片质量验收，包括：

- TTS 语气、停顿和字幕断句。
- 图片、字幕与配音时间轴对应。
- 竖屏版式、Zoom In 和转场效果。
- Worker 启动、失败恢复和网页重跑体验。
- 多条真实样片的端到端回归。

如果此时并行开发播客流程，会同时扩大脚本、TTS、渲染、页面和数据模型的变更范围，不利于定位当前主流程问题。

因此本阶段只沉淀方案，不创建播客数据库迁移、Worker stage、页面或提示词。

## 3. 产品目标

面向需要将书籍、知识内容或已有文案转为双人对谈视频的创作者，提供一条可审核、可重跑、音画严格对齐的制作流程。

目标体验：

1. 用户选择“双人对话播客”任务类型并提交资料或最终稿。
2. 系统生成主持人和嘉宾的结构化对话稿。
3. 用户检查事实、角色分配、语气和轮次后确认。
4. 系统使用两种稳定音色逐轮生成配音。
5. 画面根据当前说话人切换状态并生成字幕。
6. 用户预览、局部重跑并导出 9:16 成片。

## 4. MVP 范围

### 4.1 MVP 包含

- 两个固定角色：主持人 A、嘉宾 B。
- 从已确认文本或资料生成结构化对话稿。
- 对话稿人工审核门。
- 两种 TTS 音色及逐轮音频生成。
- 角色级字幕、停顿和完整时间轴。
- 固定双人播客版式。
- 当前说话人高亮、轻微 Zoom、亮度变化或镜头切换。
- 9:16 成片预览、重跑和下载。
- 对话稿、音频、字幕、画面和成片的版本绑定。

### 4.2 MVP 明确不做

- 不做 I2V 人物动作生成。
- 不做口型同步。
- 不做第三位嘉宾或多人圆桌。
- 不做实时录制或直播。
- 不自动联网补充未经用户确认的新事实。
- 不生成无法追溯到输入资料的观点、案例或数据。
- 不与当前单人任务共用同一阶段状态图。

## 5. 工作流设计

### 5.1 `podcast_prepare`：资料准备

输入：

- 已确认的最终文案、书籍资料或用户输入主题。
- 可选的受众、期望时长、表达风格和重点问题。

输出：

- 可引用的事实单元。
- 核心观点和禁用表达。
- 目标时长对应的字数预算。
- 角色设定和对话结构约束。

校验：

- 输入为空时不进入下一阶段。
- 资料之间存在冲突时进入人工确认。
- 健康等敏感内容继续使用现有合规规则。

### 5.2 `podcast_script`：结构化对话稿

生成顺序：

1. 先提取主题、核心观点和证据。
2. 形成开场、问题展开、案例解释、总结和 CTA 大纲。
3. 将大纲拆为对话轮次。
4. 为每一轮绑定来源范围和表达意图。
5. 运行事实、角色、长度和合规校验。

推荐角色分工：

- 主持人 A：开场、提问、追问、承接、总结。
- 嘉宾 B：解释观点、给出例子、澄清边界、总结方法。

推荐约束：

- 每轮 1 至 3 句，避免长篇独白。
- 单个发言建议 12 至 45 个汉字，按语义完整性动态调整。
- 主持人不重复嘉宾完整答案。
- 嘉宾不连续输出多个没有互动的长段落。
- 问答必须自然承接，不能只在原稿前机械添加“你怎么看”。
- 每个事实性发言必须能追溯到输入资料。

### 5.3 `podcast_review`：人工审核门

页面能力：

- 按轮次展示角色、文本、来源和预计时长。
- 支持编辑文本、切换角色、拆分、合并和调整顺序。
- 支持试听单轮角色音色。
- 显示无来源内容、敏感表达和过长发言提醒。
- 用户确认后形成唯一的 `approved_dialogue_script`。

未确认的对话稿不得进入完整 TTS 和成片阶段。

### 5.4 `podcast_tts`：双音色配音

处理原则：

- 每个对话轮次独立生成音频，失败时只重跑当前轮次。
- 主持人和嘉宾绑定不同音色及默认语速。
- 标点保留在 TTS 输入中，用于语气和停顿。
- 字幕继续使用无标点、语义完整的显示文本。
- 每轮记录真实音频时长和字符范围。
- 合并前统一采样率、声道、响度和静音规格。

音频合成顺序：

```text
角色音色选择
  → 逐轮 TTS
  → 轮次内部字幕时间戳
  → 轮次间停顿
  → 响度标准化
  → 完整播客音轨与全局时间轴
```

### 5.5 `podcast_visual`：角色画面状态

MVP 使用稳定的二维画面方案：

- 固定双人播客场景或左右角色布局。
- 当前说话人提高亮度、轻微放大或切换近景。
- 非当前说话人降低亮度或保持中景。
- 说话人变化使用短叠化，不频繁闪切。
- 角色姓名、身份和字幕拥有稳定安全区。
- 可穿插与当前对话对应的书籍、观点或案例图片。

视觉状态由对话时间轴确定，不根据音量临时猜测当前说话人。

### 5.6 `podcast_render`：成片合成

输入：

- 已确认对话稿版本。
- 完整双人音轨和角色时间轴。
- 角色素材、插图和版式配置。
- 字幕、标题、作者或嘉宾信息、免责声明。

输出：

- 标准 1080×1920 MP4。
- 角色/字幕/画面全局时间轴。
- 渲染参数、输入版本和预检报告。

渲染前必须检查：

- 所有对话轮次都有音频。
- 当前说话人与音色、字幕一致。
- 总时间轴连续且无负时长。
- 字幕不超过安全区。
- 人物和文字不存在遮挡。
- 成片时长与完整音轨误差在允许范围内。

## 6. 对话稿数据契约

建议使用结构化 JSON，避免从自由文本中解析角色和时间信息：

```json
{
  "version": 1,
  "title": "为什么越着急越容易做错决定",
  "target_duration": 180,
  "roles": {
    "host": {
      "display_name": "主持人",
      "voice": "voice_a"
    },
    "guest": {
      "display_name": "嘉宾",
      "voice": "voice_b"
    }
  },
  "turns": [
    {
      "id": "turn_001",
      "speaker": "host",
      "text": "为什么人在着急的时候反而更容易做错决定？",
      "subtitle_text": "为什么越着急越容易做错决定",
      "intent": "opening_question",
      "source_spans": ["source_01"],
      "emotion": "curious",
      "pause_after": 0.3
    },
    {
      "id": "turn_002",
      "speaker": "guest",
      "text": "因为着急会缩窄注意范围，让人更容易忽略关键信息。",
      "subtitle_text": "着急会让人忽略关键信息",
      "intent": "explanation",
      "source_spans": ["source_01"],
      "emotion": "calm",
      "pause_after": 0.8
    }
  ]
}
```

必须保留两种文本：

- `text`：包含标点，供 TTS 表达语气。
- `subtitle_text`：去除标点并按语义切分，供字幕显示。

## 7. 数据与产物隔离

建议在任务层增加独立的 `workflow_kind`：

- `single_narration`：当前八阶段单人解读流程。
- `two_person_podcast`：未来双人播客流程。

Worker 根据 `workflow_kind` 选择阶段图，不把播客阶段加入当前全局 `STAGE_ORDER`。

建议产物类型：

- `podcast_sources.json`
- `podcast_script_draft.json`
- `podcast_script_approved.json`
- `podcast_turn_audio/{turn_id}.mp3`
- `podcast_audio.mp3`
- `podcast_subtitles.json`
- `podcast_visual_timeline.json`
- `podcast_final.mp4`

所有下游产物必须记录上游版本，避免编辑对话稿后继续使用旧音频或旧成片。

## 8. 页面信息架构

### 8.1 新建任务

使用分段控件选择：

- 单人图文解读。
- 双人对话播客。

播客模式额外字段：

- 主持人定位。
- 嘉宾定位。
- 目标时长。
- 对话风格。
- 希望重点讨论的问题。

### 8.2 播客任务详情

播客详情页使用独立阶段导航，不复用当前八阶段文案：

```text
资料 → 对话稿 → 审核 → 双人配音 → 画面 → 成片
```

核心工作区优先支持对话轮次编辑和逐轮试听，而不是只展示最终 JSON。

## 9. I2V 定位

I2V 不作为 MVP 的核心渲染方式。

原因：

- 人脸、服装和背景可能在轮次间漂移。
- 长视频逐段生成成本和耗时较高。
- 人物动作不一定匹配具体发言。
- 难以保证字幕、说话人和画面严格同步。
- 单段失败可能导致人物一致性中断。

后续可将 I2V 作为可选视觉后端，仅用于：

- 开场或转场的短镜头。
- 经过人工确认的重点轮次。
- 固定角色参考图的一致性测试。

即使启用 I2V，结构化对话稿、双音色和全局时间轴仍应是主链，不由 I2V 决定内容或时长。

## 10. 实施批次

### P0：技术验证

- 使用 1 篇现有最终稿手工制作 60 至 90 秒结构化对话稿。
- 验证双音色逐轮合成、停顿和完整时间轴。
- 使用静态双人画面生成一个本地样片。
- 不修改生产任务表和当前流程。

完成标准：证明角色、字幕、音频和画面能够稳定对应。

### P1：独立任务和阶段图

- 增加 `workflow_kind`。
- 为播客建立独立阶段模板和 Worker 路由。
- 保证现有任务默认仍走 `single_narration`。

### P2：对话稿与审核

- 实现结构化脚本生成和校验。
- 实现对话轮次编辑、来源查看和确认门。

### P3：双音色与时间轴

- 实现逐轮 TTS、局部重跑、响度统一和音频拼接。
- 生成角色级字幕和全局时间轴。

### P4：播客画面与渲染

- 实现固定双人版式、说话人状态和插图能力。
- 生成 9:16 成片并完成预检。

### P5：真实样片验收

- 至少使用 3 个不同主题样本。
- 记录脚本修改量、角色串音、字幕同步和成片可用度。
- 达到验收门后再评估 I2V 或口型同步。

## 11. 验收标准

### 11.1 对话稿

- 每个事实性发言都有来源。
- 两个角色职责稳定，不出现角色人格随机互换。
- 对话自然承接，不是两段独白交替。
- 用户编辑后刷新页面内容不丢失。
- 未审核对话稿不能进入完整 TTS。

### 11.2 音频与字幕

- 两个角色音色可明显区分且不串用。
- 无明显响度跳变、截音或重复音频。
- 停顿符合语义和角色切换。
- 字幕与当前角色、音频时间严格对应。
- 单轮重跑不会改变其他已确认轮次。

### 11.3 画面与成片

- 当前说话人状态正确。
- 切换柔和，不出现频繁闪烁。
- 人物、姓名、字幕和插图不互相遮挡。
- 总时长与音轨一致。
- 成片可以在网页预览并正常下载。

## 12. 主要风险与兜底

| 风险 | 影响 | MVP 兜底 |
|---|---|---|
| 对话稿自由发挥 | 事实偏离来源 | 强制 `source_spans`，无来源轮次阻塞审核 |
| 角色发言过长 | 对话感弱 | 长度检查并提示拆分 |
| 双音色响度差异 | 听感不稳定 | 合并前响度标准化 |
| 网络导致单轮 TTS 失败 | 整体任务失败 | 逐轮产物、有限重试和局部重跑 |
| 字幕角色错位 | 用户难以理解 | 由结构化轮次直接生成时间轴 |
| I2V 人物漂移 | 视觉不一致 | MVP 不启用 I2V，使用固定角色素材 |
| 播客改动影响现有流程 | 当前主链回归 | 独立 `workflow_kind`、阶段图和回归测试 |

## 13. 启动门

满足以下条件后才启动 P0：

- [ ] 当前单人流程的 Zoom、转场、字幕、版式通过用户验收。
- [ ] TTS 停顿和字幕语义切分形成稳定基线。
- [ ] 图片、字幕和配音时间轴通过多条样片验证。
- [ ] Worker 启动、失败恢复和重跑机制可稳定使用。
- [ ] 当前流程至少完成 3 条真实样片回归。
- [ ] 用户确认播客 MVP 的角色风格、目标时长和视觉方向。

在启动门完成前，本文件仅作为初步规划，不代表功能已开发或上线。

## 14. 开发素材卡

- 阶段：规划阶段。
- 本轮主题：提前定义双人对话播客，但不分散当前单人主流程的优化资源。
- 关键模块：结构化对话稿、人工审核门、双音色 TTS、角色时间轴、播客渲染。
- 解决的问题：避免未来直接在现有八阶段流程中堆叠播客逻辑，造成状态和产物混用。
- 用户价值：播客功能启动时已有清晰边界、执行顺序和验收门槛。
- 关键设计决策：业务流程独立，基础设施复用；MVP 不采用 I2V。
- 验证证据：当前项目已有 TTS、字幕时间轴、图片渲染和成片能力可供后续复用。
- 待验证/边界：播客脚本自然度、双音色听感和角色画面均未开发、未验证、未上线。
- 可写角度：为什么新增内容形态时，先隔离工作流比直接复用旧阶段更重要。

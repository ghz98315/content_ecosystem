# AI 图书带货视频创作台 — V1 开发文档

> 项目代号：content_ecosystem
> 版本：V1 方案（2026-07-01）
> 目标：把零散的视频创作链路做成一个单界面 web 工具

---

## 1. 项目背景与目标

### 1.1 现状痛点
当前工作流由多个软件零散拼凑：

- 浏览抖音热门视频 → 人工筛选
- Excel 手工记录选题（标题、播放数据、博主信息，来回复制粘贴）
- 三方工具生成逐字稿
- ChatGPT 改写文案（来回切窗口）
- 剪映手工剪辑（重复操作最重）

**核心痛点**：提取抖音元数据、粘贴 Excel、来回切窗口的时间，比真正写内容还长。

### 1.2 V1 唯一成功标准
> 在这个工具里，从**粘贴一段抖音分享链接**，到**导出一条带字幕的竖版（9:16）成片**，**全程不切换其他软件**。

### 1.3 设计原则
- 所有中间产物（逐字稿、改写候选、音频、字幕、素材、成片）挂在**同一个任务**下持久化
- 每个环节状态**可见、可改、可重跑**
- V1 先跑通闭环，不追求功能完整

## 2. 整体架构

### 2.1 三层结构

```
┌─────────────────────────────────────────────────────────┐
│  Vercel: Next.js 前端 + 轻 API                            │
│  单界面：任务列表 | 流水线步进器 | 预览(播放器/稿件/字幕编辑) │
└───────────────┬─────────────────────────────────────────┘
                │  Supabase JS(读写 / Realtime订阅 / Storage签名URL)
┌───────────────▼─────────────────────────────────────────┐
│  Supabase(云)                                            │
│  · Postgres：tasks / stages / artifacts(状态可见可改)     │
│  · Storage：视频/音频/字幕/成片 全部产物持久化              │
│  · Realtime：状态变更实时推到前端                          │
│  · Auth：单账号登录 + RLS(避免公网裸奔)                   │
└───────────────▲─────────────────────────────────────────┘
                │  supabase-py(拉任务 / 传产物 / 更新状态)
┌───────────────┴─────────────────────────────────────────┐
│  本地电脑 Python worker(常驻循环)                         │
│  抖音解析 → 下载 → faster-whisper → OpenAI改写 → edge-tts  │
│  → ffmpeg 模板混剪+烧字幕 → 上传成片                       │
│  所有外部密钥(OpenAI key 等)只存在这里，绝不进浏览器       │
└─────────────────────────────────────────────────────────┘
```

### 2.2 关键设计决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 部署形态 | Vercel + Supabase + 本地 worker | Vercel serverless 跑不了 whisper/ffmpeg 重活 |
| 重活位置 | 本地电脑常驻 worker | 省服务器钱、用本机算力、住宅 IP 抖音风控更宽松 |
| 抖音采集 | 自研解析（首选）→ 第三方 API（备用）→ 手动上传（兜底） | 三级降级：免费自研优先，失效自动切付费第三方，都不行再手动上传 |
| LLM 改写 | OpenAI SDK | key 只放本地 worker，不进浏览器 |
| TTS 配音 | edge-tts | 免费、中文音色够用、自带词级时间戳 |
| 混剪画面 | JSON 模板引擎 + ffmpeg | V1 先 1 套图书带货模板，引擎可扩展 |

### 2.3 重活为什么必须在本地
抖音视频下载、Whisper 逐字稿、ffmpeg 混剪渲染都是**长时间、有状态、吃 CPU/磁盘**的任务。Vercel serverless 函数最长执行 10–300 秒、无持久文件系统、装不了 ffmpeg、跑不动 whisper。所以：

- Vercel/Supabase 只承载：**前端 + 轻量 API + 数据库 + 存储 + 实时推送**
- 真正的视频处理：**本地 worker**

**取舍**：电脑不开机则不处理任务（已确认接受）。

## 3. 数据模型

一切挂在同一任务下，状态可见 / 可改 / 可重跑。

### 3.1 tasks（一条视频一行）
| 字段 | 类型 | 说明 |
|---|---|---|
| id | uuid | 主键 |
| source_url | text | 抖音分享链接 |
| title | text | 视频标题（采集或手填） |
| play_count | bigint | 播放量 |
| author | jsonb | 博主信息（昵称/id/粉丝数等） |
| status | text | 总状态 |
| created_at / updated_at | timestamptz | |

### 3.2 stages（每任务 5 个阶段行）
| 字段 | 类型 | 说明 |
|---|---|---|
| id | uuid | 主键 |
| task_id | uuid | 外键 → tasks |
| kind | text | ingest / transcribe / clean / rewrite / tts / image / book / render（8 阶段） |
| status | text | pending → processing → done / failed / **needs_review** |
| params | jsonb | 阶段参数，**可编辑** |
| input_ref | text | 输入产物引用 |
| output_ref | text | 输出产物引用 |
| error | text | 失败信息 |
| updated_at | timestamptz | |

### 3.3 artifacts（产物，指向 Supabase Storage）
| 字段 | 类型 | 说明 |
|---|---|---|
| id | uuid | 主键 |
| task_id | uuid | 外键 → tasks |
| stage_kind | text | 归属阶段 |
| type | text | video / transcript / clean / rewrite / audio / image / book / subtitle / final |
| storage_path | text | Supabase Storage 路径 |
| meta | jsonb | 时长/分辨率/字数等元信息 |

### 3.4 核心机制
- **重跑**：把某 stage 重置为 `pending` → worker 重新处理；下游 stage 自动失效等待。
- **评审门**：`rewrite`（挑改写候选）和 `book`（书名识别不出时人工复核）两处置为 `needs_review`，暂停等你确认再往下走。这就是"可改"。
- **实时**：worker 每次改 stage 状态，Supabase Realtime 推到前端，进度可见。

## 4. 八阶段流水线

> 本流水线依据一份已跑通商业化的同类工具实现拆解修正而来（健康/图书带货赛道，单条成本 6–8 毛，约 15 分钟出片）。核心认知：**原视频不进成片，只用来出逐字稿；成片画面是文案逐句生成的 AI 意境图**。

映射你现有链路：

| 阶段 | 你现在的动作 | 工具里的实现 | 产物 |
|---|---|---|---|
| ① 采集 ingest | 浏览抖音 + Excel 记录 | 粘贴分享链 → 解析拿视频 + 标题/播放量/博主，自动入库。**三级降级：自研解析 → 第三方 API → 手动上传兜底** | 原视频/音频 + 元数据 |
| ② 逐字稿 transcribe | 找三方工具 | faster-whisper 出**带词级时间戳**逐字稿 | 原始 transcript.json |
| ③ 清洗 clean | —（新增） | LLM 修错字/重断句/数字转中文/删引导话术/代词换真实书名（详见 4.2） | 清洗后正文 |
| ④ 改写 rewrite | ChatGPT 来回切 | OpenAI 出多个改写候选，UI 挑一条 / 再编辑（**评审门**） | rewrite 候选 |
| ⑤ 配音 tts | —（新增） | edge-tts 合成，自带 WordBoundary 词级时间戳（字幕对齐直接可用） | audio.mp3 + 词时间戳 |
| ⑥ 生图 image | 剪映找素材 | 文案按句切片 → OpenAI 生意境图（**9 宫格省钱**，详见 4.3）→ 医疗安全转译（4.4） | 逐句场景图 |
| ⑦ 书籍信息 book | —（新增） | LLM 反推真实书名/作者/国籍 + 生成视频号标题（长标题带话题 + 短标题封面）。书名识别不出 → **评审门**人工复核 | 书籍信息 + 标题候选 |
| ⑧ 成片 render | 剪映手工 | 模板引擎：逐句图 + TTS 音频 + 对齐字幕 + 片头书封卡 + 片尾免责声明 → 输出 9:16 竖版 → 导出 | final.mp4 |

**为什么原视频不进成片**：参考实现里原视频只用于第 ② 步出逐字稿，成片全部是 AI 生成的意境图幻灯片 + 动效。这既是图书带货的常见形态，也规避了搬运原视频的搜高索/侵权风险。

### 4.1 采集解析器（三级降级，可切换）

抖音接口经常变，采集环节做成**统一接口 + 多后端**，互不影响主流程：

```
DouyinResolver（统一接口：输入分享链 → 输出 视频/音频URL + 元数据）
  ├─ 1. SelfResolver        自研解析（免费，首选）
  ├─ 2. ThirdPartyResolver  第三方 API（如 TikHub 等，付费，备用）
  └─ 3. ManualUpload        手动上传视频 + 手填元数据（兜底，永远可用）
```

- 默认走自研解析；抛异常或拿不到地址 → **自动降级**到第三方 API。
- 第三方也失败（或没配 key）→ stage 置为 `needs_review`，前端提示手动上传、手填标题/播放量。
- 第三方 key 配在本地 worker 环境变量，**没配就跳过第二级**，直接自研→手动。
- 每个 resolver 独立模块，抖音改接口时只修 `SelfResolver` 一处，不动主流程。

### 4.2 逐字稿清洗规则（第 ③ 步，参考实现踩坑总结）

抖音 ASR 原始逐字稿错字极多，清洗是独立于"改写"的一步，交 LLM 一次处理：

- **修错字**：尤其人名、书名、专有名词（例：医疗类「嘌呤」被识别成「飘铃」、「胰岛素」成「衣岛素」）。整段丢给 LLM 带上下文修更准。
- **重新断句**：ASR 断句混乱，重排成自然句读。
- **数字转中文**：十/百/千/万等**必须转中文**——否则 TTS（如 index-tts2）易把数字念成个位数。edge-tts 也建议统一转中文规避风险。
- **删引导话术**：去掉博主的"点赞收藏""关注我"等引导文案。
- **模糊代词换书名**：把"这本书"这类含糊代词替换为具体书名。

### 4.3 逐句生图 + 9 宫格省钱（第 ⑥ 步）

- 文案**按句切片**，每句生成一张对应意境图（10 分钟视频约 64 张）。
- **省钱关键**：一次生图请求让模型出 **9 宫格大图**，系统内部自动切割成 9 张（用户无感）。成本可降约 90%——参考实现 63 张图成本 ≈ 0.5 元。
- OpenAI 生图；模型层做薄封装，后续可换国内便宜模型。
- 每张图 UI 可单独"重生成此图"。

### 4.4 医疗/敏感内容安全转译（第 ⑥ 步红线）

健康赛道最大的坑：**即使文案讲糖尿病/癌症/肾衰竭，也不能生成病房、ICU、病理图等画面**，否则平台提醒甚至限流。

- 生图前对敏感段落做**转译**：把病症画成"日常生活方式隐喻"。
  - 例：「糖尿病晚期」→ 画「老人独自在厨房手抖打翻东西」，而非「医院 ICU 监护仪」。
- 维护违规词/敏感场景清单，生图 prompt 前过一遍。

### 4.5 成片模板引擎（第 ⑧ 步）

参考实现是**矩阵式**：4 种风格 ×（多种动效预设），一次可批量出多风格成片。

- **风格**（参考）：清醒语录 / 黑底打字机 / 暗色知识卡片 / 图书口播卡片。
- **动效预设**（参考）：电影感(交叉溶解+Ken Burns 慢移) / 动感快剪 / 禅意静帧 / 胶片复古。
- **片头**：书封卡（书名 + 作者）。**片尾**：免责声明模板，支持占位符 `{author}`/`{title}`，例：
  > 本视频基于{author}《{title}》及相关研究资料整理
  > 仅用于健康科普分享，不构成任何建议或行为指导
- **字幕**：用第 ⑤ 步 TTS 词级时间戳对齐，烧进画面。
- 由模板引擎 + ffmpeg 渲染，输出 9:16。

**V1 范围**：先做 **1 种风格 + 1 种动效**跑通闭环，引擎设计成可加风格/动效，多风格矩阵放 M6。

## 5. 里程碑计划（先烧风险，再深化）

| 里程碑 | 内容 | 验证重点 |
|---|---|---|
| **M0 骨架** | Supabase 建表 + RLS、worker 认领循环、Vercel UI 壳、一条假任务走完 8 阶段状态流转 | **最高风险：本地 worker ↔ 云 ↔ 前端 实时联通** |
| **M1 采集** | 抖音解析 + 下载 + 元数据，含手动上传兜底 | 第二高风险，提前验证 |
| **M2 逐字稿** | whisper 词级时间戳 | |
| **M3 清洗** | LLM 修错字/断句/数字转中文/删引导/换书名 | |
| **M4 改写** | OpenAI 候选 + 挑选/编辑评审门 | |
| **M5 配音** | edge-tts + 词边界时间戳 | |
| **M6 生图** | 逐句切片 + OpenAI 生图 + 9 宫格切割 + 医疗安全转译 | **新增核心环节，成本大头** |
| **M7 书籍信息** | LLM 反推书名/作者 + 视频号标题 + 识别不出评审门 | |
| **M8 成片** | 模板引擎（1 风格 1 动效）+ 逐句图 + TTS + 对齐字幕 + 书封卡 + 免责声明 + 9:16 导出 | **← 唯一成功标准在此达成** |

**排期逻辑**：M0、M1 是全链路最不确定的两环（本地↔云联通、抖音解析），优先烧掉。M6 生图是新增核心且成本大头，需重点验证 9 宫格切割与医疗安全转译。whisper / edge-tts / ffmpeg 都是成熟件，风险低。

- Tailwind CSS

- 云连接：supabase-py

## 7. 需要准备的前置条件

### 6.3 大模型选型（按参考实现的成熟选择）

| 环节 | 模型 | 理由 | 可切换 |
|---|---|---|---|
| 清洗 clean | OpenAI | 带上下文修错字/断句更准 | 是 |
| 改写 rewrite | OpenAI | 你已定 | 是 |
| 书名反推 book | **deepseek-v4-flash** | 参考验证：成本低（≈0.002 元/次）且准，gpt 系列要么识别不出要么贵 | 是 |
| 生图 image | **gpt-image（OpenAI）** | 参考同款，9 宫格切割控成本 | 是 |
| 配音 tts | **edge-tts** | 免费 + 词级时间戳（字幕对齐直接可用）；参考的 index-tts2 需显卡/三方 API、慢且贵，V1 不用，语音克隆放后续 | 是 |

所有模型走**统一薄封装 + 环境变量配置**，切模型只改 config，不动主流程。

## 7. 需要准备的前置条件

1. **Supabase 项目**（免费档够用）：URL + anon key（前端）+ service_role key（worker）
2. **OpenAI API key**：清洗 / 改写 / 生图用，只放本地 worker
3. **DeepSeek API key**：书名反推用（deepseek-v4-flash，便宜）；没配则 fallback 到 OpenAI
4. **第三方抖音解析 API（可选，备用）**：如 TikHub 等的 key，配了才启用第二级降级；不配则走自研→手动
5. **本地环境**：Python 3.10+、已装 ffmpeg、能连外网（edge-tts 走微软服务）；GPU 可选（whisper 更快，CPU 也能跑）
6. **Node 环境**：Node 18+（前端开发 / 部署 Vercel）

---

## 8. V1 明确不做（避免范围蔓延）

- 多用户 / 团队协作
- 云端 GPU
- 多风格矩阵（4 风格 ×4 动效，V1 先 1×1）
- 语音克隆（V1 用 edge-tts，index-tts2/克隆放后续）
- 批量流水线（一次跑多条）
- 数据分析看板
- 多平台（只做抖音）

以上留到跑通闭环之后再迭代。（注：AI 生成图片素材已纳入 V1 核心，见第 4.3 节）
